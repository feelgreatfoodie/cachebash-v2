### Iteration 2: 2026-01-30T23:30:00Z
#### Story: [US-002] Add Real-Time Updates to Messages

**Root Cause Analysis:**
The `activeMessagesProvider` merged two collections (`/messages` and `/questions`) but used different fetching strategies:
- `/messages`: Used `.snapshots()` stream (real-time updates worked)
- `/questions`: Used `.get()` one-time fetch (no real-time updates)

This meant messages from the unified collection updated in real-time, but legacy questions only loaded on initial fetch or manual refresh.

**Implementation:**
1. Created `_combineStreams` helper function to implement combineLatest pattern
   - Takes two Firestore snapshot streams and combines them
   - Emits a tuple when either stream emits (after both have initial values)
2. Created `_mergeStreams` helper function to merge two streams into one
3. Refactored `activeMessagesProvider` to:
   - Create separate streams for both `/messages` and `/questions`
   - Use `_combineStreams` to merge them with real-time updates for both
   - Deduplicate messages by ID before returning

**Files Changed:**
- `app/lib/providers/messages_provider.dart` - Added stream combining helpers and refactored activeMessagesProvider

**Verification:**
- Flutter analyze passes with no errors (only pre-existing warnings)
- Both collections now use Firestore `.snapshots()` listeners
- Messages update in real-time when either collection changes

**Learnings for Future Iterations:**
- Dart's `async*` generators work well for implementing Rx-style stream combinators
- The `(T1, T2)` record syntax (Dart 3) is convenient for tuples without external packages
- When merging data from multiple Firestore collections, ensure all use stream listeners for consistency

### Iteration 3: 2026-01-30T23:45:00Z
#### Story: [US-003] Fix Sessions Not Appearing on Home Screen

**Root Cause Analysis:**
Sessions were not appearing on the home screen due to a Firestore query issue. The Flutter app queries sessions with:
```dart
.where('archived', isNotEqualTo: true)
```

However, when the MCP server's `updateStatus` tool created sessions, it did NOT set the `archived` field at all. In Firestore, `isNotEqualTo` queries do NOT match documents where the field is missing - they only match documents where the field exists and has a different value.

**Implementation:**
Added `archived: false` to the session data in `updateStatus.ts` so that newly created sessions explicitly have the `archived` field set, making them match the query.

**Files Changed:**
- `mcp-server/src/tools/updateStatus.ts` - Added `archived: false` to sessionData

**Verification:**
- MCP server builds successfully (`npm run build`)
- Flutter analyze passes with no new errors
- New sessions will now appear in the active sessions query

**Learnings for Future Iterations:**
- Firestore `isNotEqualTo` queries do NOT match documents where the field is missing
- Always explicitly set boolean fields rather than relying on defaults
- When debugging "missing data" issues, check if the query filter matches documents without the field

### Iteration 4: 2026-01-31T00:00:00Z
#### Story: [US-004] Fix Archive Error Document Not Found

**Root Cause Analysis:**
The `activeMessagesProvider` merges messages from two Firestore collections:
- `/messages` (new unified collection)
- `/questions` (legacy collection)

When the user archives a message, `MessagesService.archiveMessage()` only tried to update the `/messages` collection. If the message was a legacy question from `/questions`, the update would fail with "document not found" because the document doesn't exist in `/messages`.

**Implementation:**
Updated three methods in `MessagesService` to handle both collections:
1. `archiveMessage()` - Check if document exists in `/messages` first, fall back to `/questions`
2. `unarchiveMessage()` - Same dual-collection logic
3. `deleteMessage()` - Same dual-collection logic

The approach:
1. Check if document exists in `/messages` via `.get()`
2. If exists, update there and return
3. If not, check `/questions` collection
4. If exists there, update and return
5. If neither, throw Exception for clear error message

**Files Changed:**
- `app/lib/providers/messages_provider.dart` - Updated archiveMessage, unarchiveMessage, and deleteMessage methods

**Verification:**
- Flutter analyze passes with no new errors (only pre-existing warnings)
- iOS build succeeds
- Archive/unarchive/delete operations now work for both unified and legacy messages

**Learnings for Future Iterations:**
- When the app merges data from multiple collections, all CRUD operations must handle both collections
- Use `.get()` to check document existence before `.update()` to avoid "not found" errors
- The MCP server writes to both collections for backwards compatibility, but the Flutter app reads from both

### Iteration 11: 2026-01-31T05:00:00Z
#### Story: [US-011] Fix X Button on Compose Screen

**Root Cause Analysis:**
The X button on the compose screen (CreateMessageScreen) uses `context.pop()` to close the screen. However, the compose button in MainShellWrapper was using `context.go('/messages/new')` instead of `context.push('/messages/new')`.

With go_router:
- `go()` replaces the current route in the navigation stack
- `push()` adds the route on top of the current stack
- `pop()` removes the top route from the stack

When `go()` is used, the previous route is replaced rather than preserved, so when `pop()` is called, there's nothing to pop back to, and the screen doesn't close properly.

**Implementation:**
Changed the compose button in MainShellWrapper from `context.go('/messages/new')` to `context.push('/messages/new')`. This ensures the compose screen is pushed onto the navigation stack, allowing `pop()` to work correctly.

**Files Changed:**
- `app/lib/widgets/main_shell.dart` - Changed `context.go` to `context.push` for compose button

**Verification:**
- Flutter analyze passes with no new errors
- iOS build succeeds
- X button now properly closes the compose screen by popping the navigation stack

**Learnings for Future Iterations:**
- In go_router, use `push()` when you need a "back" button to work; use `go()` for top-level navigation changes
- For modal/overlay screens like compose, always use `push()` so `pop()` works correctly
- The messages_screen.dart FAB already used `push()` - this was just the compose button in bottom nav that was wrong

#### Story: [US-012] Add Keyboard Dismiss Behavior

**Implementation:**
Added keyboard dismiss behavior to all screens with text input fields. Tapping outside the keyboard now dismisses it.

**Approach:**
Wrapped each screen's Scaffold with a GestureDetector that calls `FocusScope.of(context).unfocus()` on tap. This is the standard Flutter pattern for dismissing the keyboard when tapping outside input fields.

**Files Changed:**

- `app/lib/screens/search/search_screen.dart` - Added GestureDetector wrapper

- `app/lib/screens/auth/login_screen.dart` - Added GestureDetector wrapper
- `app/lib/screens/auth/register_screen.dart` - Added GestureDetector wrapper
- `app/lib/screens/settings/profile_screen.dart` - Added GestureDetector wrapper
- `app/lib/screens/settings/change_password_screen.dart` - Added GestureDetector wrapper

**Pattern Used:**
```dart
void _dismissKeyboard() {
  FocusScope.of(context).unfocus();
}

@override
Widget build(BuildContext context) {
  return GestureDetector(
    onTap: _dismissKeyboard,
    child: Scaffold(...),
  );
}
```

**Verification:**
- Flutter analyze passes with no new errors
- iOS build succeeds
- Tapping outside text fields now dismisses the keyboard

**Learnings for Future Iterations:**
- `FocusScope.of(context).unfocus()` is the standard way to dismiss keyboard in Flutter
- Wrapping Scaffold with GestureDetector is cleaner than using `keyboardDismissBehavior` on ScrollViews
- This pattern should be applied to all screens with text input for consistent UX
